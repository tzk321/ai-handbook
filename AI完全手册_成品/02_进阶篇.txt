╔══════════════════════════════════════════════════════════╗
║ 第 1 章 · 心智模型：AI 的能力是分层的                        ║
╚══════════════════════════════════════════════════════════╝

先建立一个图，后面所有内容都挂在这张图上：

  ┌────────────────────────────────────────────────────┐
  │ ① 人格层      它是谁、怎么说话                       │ 门槛：无
  ├────────────────────────────────────────────────────┤
  │ ② 工具层      它有什么"手"（能读文件、跑命令）        │ 门槛：无
  ├────────────────────────────────────────────────────┤
  │ ③ 宿主层      手能伸到手机多深（要不要 root）          │ 门槛：要 root
  ├────────────────────────────────────────────────────┤
  │ ④ 容器层      给它一个独立的家（完整 Linux）          │ 门槛：root + 空间
  ├────────────────────────────────────────────────────┤
  │ ⑤ 云端层      出门办事（24 小时在线的服务器）          │ 门槛：花钱
  └────────────────────────────────────────────────────┘
              + 胶水层：技能（把"怎么干活"写成手册）

【三条底层规律，先记住】

  规律一：**上层能力来自下层权限。**
    它能不能读文件，取决于 App 有没有那个权限；
    它能不能跑系统命令，取决于你有没有 root。
    所以"AI 干不了某事"99% 不是 AI 的问题，是**你没给它那层权限**。

  规律二：**一层出问题，只查那一层。**
    分层最大的好处是排错：人格不对 → 查提示词；
    命令跑不动 → 查工具层；命令跑对了但结果不对 → 查宿主层（权限/命名空间）；
    环境太脏 → 查容器层。

  规律三：**每层的成果都要落盘。**
    提示词落成助手卡、流程落成技能、环境落成脚本。
    没落盘的成果，下次开新对话就没了。

【验收】
  能在纸上画出这五层，并说出每层"干不了事"时该查谁 → 过关。

║ 第 2 章 · 人格层：助手卡怎么设计                            ║
╚══════════════════════════════════════════════════════════╝

━━ 2.1 一张卡里到底有什么 ━━

现代 AI 客户端（RikkaHub 这类）的一张助手卡，字段大致分四组：

  【人格组】
    systemPrompt        系统提示词 —— 最关键，人设全文
    presetMessages      预设消息 —— 开场白，进对话就是这条
    contextTemplate     上下文模板 —— 决定"人设/场景/用户"怎么拼给模型
    messageTemplate     消息模板 —— 每条消息打包成什么样（一般别动）

  【知识组】
    lorebookIds         挂哪些世界书（关键词触发的设定）
    modeInjectionIds    挂哪些模式注入（整段固定插入的话）
    quickMessageIds     快捷消息（常用短语，一点就发）

  【干活组】
    localTools          挂哪些工具
    enabledSkills       挂哪些技能
    envTarget/envCwd    命令默认落到哪、工作目录在哪
    shellTimeout        单条命令超时（秒）
    toolExecTimeout     工具调用总超时（秒）
    enableParallelToolExecution  允许并行调用工具

  【手感组】
    temperature         温度（想象力）  留空=用默认
    topP                采样范围
    maxTokens           单次最多写多少
    contextMessageLimit 带最近多少条消息
    reasoningLevel      思考档位（low/medium/high/xhigh）
    talkativeness       话痨程度
    enableAutoCompact   聊长了自动压缩
    enableTimeReminder  是否提醒它当前时间
    enableWebSearch     联网搜索
    enableMemory / useGlobalMemory / enableAutoMemoryExtract   记忆三件套

━━ 2.2 人设怎么写（四段结构，直接照这个骨架） ━━

  第一段 · 身份
    "你是谁、几岁、在哪、干什么、跟用户什么关系"
    例：你是 XX，我认识多年的兄弟，住在我隔壁。{

  第二段 · 说话方式（**这段决定像不像人**）
    要给三种弹药：
      ① 句子长度："一行一个意思，从不写超过四行的段落"
      ② 口头禅/语气词：直接把词列出来
      ③ Emoji 规则："几乎不用；用了就是敷衍，比如 😄👍"
    例：你说话短、快、有点冲。骂人是亲昵不是攻击。
        常说的词：无米、难绷、典、拉完了。

  第三段 · 行为准则（**"不许"比"要"管用**）
    例：不许讲大道理。不许嘘寒问暖。不许写小作文。
        我问正事就正经答，答完继续贫。

  第四段 · 红线与例外
    例：遇到认知严重偏差又不听劝的人，不许争论，直接冷掉。

  【三个写作技巧】
  ① **给例子，别给形容词。**
     ✗ "说话要刻薄"   ✓ "问你借钱时回'无米'两个字"
  ② **给档位，别给单一态度。**
     对死党/对普通朋友/对陌生人，三档分别写。
     不然它对谁都是一个味，一眼假。
  ③ **长度控制在 3000 字内。** 再长它记不住，还费钱。

━━ 2.3 可以插的变量（写在提示词里，说话时自动变） ━━

  {{char}}         这个助手的名字
  {{user}}         用户的名字
  {{time}}         当前时间        {{cur_date}}    今天的日期
  {{weekday}}      星期几          {{timezone}}    时区
  {{locale}}       语言地区        {{model_name}}  当前模型
  {{device_info}}  设备信息

  用法：现在是 {{time}}，跟 {{user}} 说话别啰嗦。
  ⚠️ 变量在不同分支/版本里支持的集合可能不同，
     写完发一条消息验证一下有没有被替换。

━━ 2.4 世界书 vs 模式注入 vs 快捷消息（别用混） ━━

  世界书（关键词触发）
    什么时候用：**设定类知识**，只在谈到时才需要
    例：人物经历、地名来历、圈子黑话、后台设定
    关键字段：关键词 / 注入内容 / 常驻激活 / 注入位置 / 注入深度 / 优先级

  模式注入（开关控制）
    什么时候用：**整段常驻的东西**，需要时手动开
    例：深夜模式、工作模式、翻译模式、某种语气外壳

  快捷消息（一点就发）
    什么时候用：**你天天要打的那几句话**
    例："继续" "说人话" "重新写" "太长，短的"

  【一条经验】
  世界书条目别贪多。10 条精的，比 100 条乱的有用 ——
  条目越多，误触发越多，而且每轮都在烧 token。

━━ 2.5 记忆怎么处理（自带记忆 vs 记事文件） ━━

  自带记忆（enableMemory）
    · 优点：自动，省心
    · 缺点：① 抽什么你控制不了 ② 每轮都注入，费 token
            ③ 抽错了得手动去删，删了还没后悔药

  记事文件（写成一个技能/一组 md）
    · 优点：准确、便宜、你完全可控、能版本化
    · 缺点：得手动维护（但这活儿可以让 AI 自己干）

  【建议路线】
    阶段一：先用自带记忆，体会一下它能抽什么
    阶段二：发现"抽得不对/太贵" → 关掉，改成 md 记事本
    阶段三：把记事本包成一个技能 → AI 干活前自己会去翻

  ▸ 举例：把记忆功能全关，改用几个 md 文件来记事 —— 看得见、能改、能 diff。

━━ 2.6 参数怎么给（按用途抄） ━━

  用途            温度      上下文条数   思考档位
  ────────────────────────────────────────────────
  写代码/办事     0.2~0.5   多（80~120）  high/xhigh
  日常问答        0.6~0.8   中（40~60）   medium
  角色扮演/陪聊   0.9~1.0   中（30~50）   low/medium
  玄学/发疯        1.05+     少（20~30）   low

  · maxTokens 留空 = 不限，但可能一次狂写烧光额度；
    建议先设个 4000 试试，不够再放开。
  · enableParallelToolExecution 打开后，它能同时干几件事，
    干活卡必开（不然一条条排队，慢一倍）。

【验收】
  · 换一个新对话，它还是那个味 → 人设过关
  · 你说一句黑话，它接得上 → 世界书过关
  · 关掉 App 重开，它还记得该记的事 → 记忆方案过关

━━ 3.1 工具分几类（按功能记） ━━

  文件类    read / write / patch / list / search
  命令类    shell（沙箱内）/ 外部环境执行器（容器、root、ssh）
  代码类    Python 引擎 / JavaScript 引擎
  交互类    ask_user（反问）/ clipboard（剪贴板）/ calendar（日历）
  数据类    database_query（查 App 自己的库）
  任务类    task / todo（把多步任务拆开跟踪）
  时间类    time_info / screen_time

  【一条原则】
  工具不是越多越好。陪聊卡挂 clipboard + time_info 就够；
  干活卡才挂全套。挂多了有两个坏处：
  ① 每轮的工具描述也占 token；② 它会更爱乱用工具。

━━ 3.2 最容易搞混的一点：**沙箱命令 ≠ 系统命令** ━━

  大多数 App 的"执行命令"工具，跑起来是 **App 自己的身份**
  （Android 里叫 uid，比如 u0_a356），能碰的东西很少：
  自己那个私有目录、部分公共存储、系统只读命令。

  想让它碰到系统级别的东西，需要**另一套通道**：
  · 走 su/root（真机）
  · 走容器（droidspaces / proot / Termux）
  · 走远程（ssh）

  所以看到"卡里有 shell_tools"别高兴太早 ——
  **能不能打通，取决于那条通道，而不是那个工具名。**

  【怎么判断你的通道通没通】
    跑三条，看身份变没变：
      1. id              → 看 uid 是不是 0（root）
      2. hostname        → 看是不是容器/远程的主机名
      3. ls /data/user/0 → **这条最关键**（见 3.4）

━━ 3.3 超时与后台任务（必须掌握） ━━

  大多数 App 的单条命令工具都有硬超时（常见 30 秒）。
  超了就直接掐，而且**它可能连报错都来不及给你**。

  【两种后台方式】
    容器里： systemd-run（有日志、有状态，能查）
       systemd-run --unit=任务名 --collect /usr/bin/bash /路径/脚本.sh
       查：systemctl is-active 任务名; journalctl -u 任务名 -o cat | tail -40
    真机上： setsid + nohup，自己写日志文件
       setsid sh 脚本.sh > 日志.log 2>&1 &

  【正确姿势：两段式】
    第一步：起后台，立刻返回（别等）
    第二步：隔一会儿去查日志/状态，看有没有 DONE 标记
  · 脚本最后一行一定要打一个**明确的完成标记**（比如 echo DONE），
    不然你不知道它是跑完了还是卡住了。

  【坑】
  · 后台任务**不继承**执行器塞给你的环境变量（比如 token），
    脚本里要自己 source /etc/agent.env 之类。
  · 后台任务失败了，日志不会自己冒出来 —— 必须去翻。

━━ 3.4 权限与命名空间（最坑的一节） ━━

  症状：**"东西明明在，它说没有"。**

  原因：Android 的权限 + Linux 的挂载命名空间是两套东西。
  裸 su 进到的是一个"被遮蔽过"的命名空间：

    su -c 'ls /data/user/0'     → 可能只看到自己和 GMS
    （看着别的 App "不存在"，其实在）

  排查三步：
    ① 换身份试：直接用 root 执行器（绕过遮蔽）
    ② 换路径试：换成 /data/data 或绑定挂载点再试
    ③ 看权限位：ls -ld 看 owner/mode（uid 对不对）

  【FUSE / 外部存储的规矩】（这条踩过的人都记得住）
    Android 的 /storage/emulated/0 是 FUSE 挂的。
    它判断"你能不能读"，看的**不是 mode，是创建者**：
      · App 自己创建的文件 → 自己能读
      · root/别的 App 创建的文件 → **你这个 App 读不了**（EACCES）
      · chmod 666 也不管用（它不看这个）

    三种解法：
      ① 交付给人类看的文件 → 无所谓，文件管理器能读
      ② 自己还要读的文件 → 写到 App 私有目录
         /data/user/0/<包名>/files/
      ③ 一定要放公共目录又要自己能读 →
         **App 先创建那个文件（占位），再让 root/容器 cat > 原地覆盖**
         ⚠️ 绝对不能 mv / rename，一改创建者就废

━━ 3.5 工具自检（每次环境变动后跑一遍） ━━

  一条链跑下来，全绿才算健康：
    1. 身份：    id / whoami / hostname
    2. 位置：    pwd / ls
    3. 写入：    echo test > 某个目录/t
    4. 读回：    cat 某个目录/t
    5. 回传：    把结果文件弄到宿主机能看到的地方
    6. 长任务：  起一个后台任务，等 5 秒，查日志

【验收】
  能一句话说清"哪个身份、哪个目标、什么超时"，
  并且能自己把这三样组合成命令 → 过关。


╔══════════════════════════════════════════════════════════╗
║ 第 4 章 · 宿主层：要不要 root，怎么用                        ║
╚══════════════════════════════════════════════════════════╝

━━ 4.1 先说清楚利弊 ━━

  root 能带来什么
    · 真·执行命令、读写任意目录
    · 装容器、挂载、改系统配置
    · AI 能帮你运维这台手机（改设置、清垃圾、抓日志）

  root 的代价
    · **刷机有风险**（变砖、清数据、保修没了）
    · 解锁 bootloader 后部分银行/支付 App 会不认
    · **AI 拿到 root = 它随时能改你手机的任何东西**
      （这是最需要想清楚的一条）

  【替代方案（不想 root 的话）】
    · Shizuku：给 App 一部分 adb 级权限，能做不少事
    · Termux：纯用户态 Linux 环境，能跑很多命令行工具
    · 云服务器：把重活丢出去，手机只管聊天
    → 这三样组合起来，能覆盖 70% 的玩法。

━━ 4.2 root 之后新增的能力清单 ━━

  · 读写任意路径（包括别的 App 数据、系统分区）
  · 挂载 / 卸载（loop 镜像、绑定挂载）
  · 起真正的容器（droidspaces / chroot）
  · 改系统设置、控制服务
  · 抓内核日志、看硬件状态
  · 装内核模块 / Xposed 模块

━━ 4.3 统一执行器（**这是整套的关键零件**） ━━

  为什么需要它：
    `su -c "命令"` 的引号地狱是灾难。一层层转义，最后
    你根本不知道哪层引号出了问题。

  正确做法：**命令走 stdin，不要走参数。**

  最小可用模板（放到 /data/local/ 下，chmod 755）：

    #!/system/bin/sh
    # 用法：su -c '/data/local/exec.sh' <<'EOF'
    #       要跑的命令（引号、$、反引号全部原样）
    #       EOF
    MODE="${1:-sh}"
    SCRIPT=$(cat)                       # ← 关键：从 stdin 收明文
    case "$MODE" in
      sh)   exec /system/bin/sh -c "$SCRIPT" ;;
      root) exec /system/bin/sh -c "$SCRIPT" ;;   # 真机全局命名空间
      kali) exec /data/local/kali "$SCRIPT" ;;    # 容器
      ssh)  exec ssh 你的别名 "$SCRIPT" ;;
      *)    echo "未知模式: $MODE" >&2; exit 2 ;;
    esac

  【设计要点（都是从踩坑里总结的）】
  ① 命令**落地成文件**再执行，能根治引号问题
  ② 每个模式要有**明确的名字**，别让 AI 猜
  ③ 脚本自己只干"转发"，别塞业务逻辑
  ④ 出错要 echo 到 stderr + 返回非 0（不然就是静默失败）

  ▸ 举例：统一执行器、文件助手、容器包装，各写成一个脚本丢在 /data/local/，chmod 755。

━━ 4.4 安全边界（给 AI 开 root 之前，先把这几条立好） ━━

  ① **危险动作要审批。**
     开关类工具（比如"工具审批"）打开：它每次动手前先问你。
     宁可多点几次同意，也别让它自己删了你的东西。

  ② **给自己划禁区，写进提示词/技能里。**
     例：不许动 /system、不许卸载应用、不许改别人的模块、
         不许格式化任何分区。

  ③ **动配置先备份。**
     cp -a 文件 文件.bak.$(date +%F)
     —— 这条要写成肌肉记忆。

  ④ **重要改动要写日志。**
     "改了什么、为什么改、怎么回滚"记三行。
     两个月后你自己会感谢自己。

  ⑤ **不要在提示词里放密码。**
     密码放文件里、权限设好，让 AI 去读文件，不要写在人设里
     （人设会被发出去、会被复制、会被导出）。

【验收】
  能在真机上跑一条命令，结果和你手动 su 跑的一致；
  并且你能说出"哪些目录是它的禁区" → 过关。


╔══════════════════════════════════════════════════════════╗
║ 第 5 章 · 容器层：给它一个家                                ║
╚══════════════════════════════════════════════════════════╝

━━ 5.1 为什么值得搞一个容器 ━━

  · **隔离**：它在里面怎么折腾都行，不污染手机本体
  · **完整**：真 Linux，apt/pacman、systemd、docker 都能用
  · **可重来**：玩坏了删掉重建，几分钟的事
  · **长任务**：systemd 托管的后台任务，比 nohup 靠谱
  · **身份感**：有个固定名字和目录，AI 不会每次都从零猜

━━ 5.2 选哪个方案（按门槛排序） ━━

  方案              需要         优点                缺点
  ────────────────────────────────────────────────────────────
  Termux           无          最简单，能跑很多东西  不是真 root，系统调用受限
  proot-distro     Termux      不用 root 就有发行版   伪 root，systemd 不全
  droidspaces      root        **真容器 + 真 systemd**  要 root、要空间
  chroot 手动      root        完全可控              配置麻烦

  【建议】
    第一步：Termux 玩明白（零风险）
    第二步：想跑 systemd/docker → 上有 root 的真容器
    第三步：想 24 小时在线 → 搬去云服务器

━━ 5.3 搭一个容器要做的事（清单） ━━

  ① 拿空间：准备 8G 以上（镜像 + 里面装的软件）
  ② 建镜像/根文件系统（ext4 loop 镜像，或直接目录）
  ③ 配置网络（NAT 还是 host；需不需要固定 IP）
  ④ 选 init（真 systemd 的话，容器要支持）
  ⑤ 建普通用户 + 密码（root 别当日常账号用）
  ⑥ 配 apt/pip 国内源（不然装东西慢到怀疑人生）
  ⑦ 配时区 / 语言 / 字体
  ⑧ **建一个普通用户进 sudo，日常用它**
  ⑨ 装基础包：openssh-client、python3、curl、git、zip
  ⑩ 做一次快照/备份（玩坏了能回滚）

  【验收（做完这些才算搭好）】
    · uname -a 显示 Linux、hostname 是你起的名字
    · systemctl status 有真 systemd
    · 能 apt update 且够快（说明源配对了）
    · 能连外网（curl -sI https://api.github.com | head -1）

━━ 5.4 宿主机 ⇄ 容器的文件通道（三种，各有各的坑） ━━

  ① 绑定挂载（**最爽，优先用**）
     把宿主某个目录 bind 到容器里：
       宿主 /data/user  →  容器 /mnt/data/user
     结果：两边是**同一份 inode**，写哪边都一样。
     坑：
       · 挂载点里**看不到 bind 的内容**（bind 只活在容器的 namespace 里）
       · 权限：容器里普通用户可能进不去（一般只放给 root）

  ② 经宿主挂载点直读容器盘（容器在跑才有）
     宿主 /mnt/<容器名>/... = 容器的 /
     用途：容器挂了也能救文件
     坑：容器没运行时这个挂载点是**空的**，容易误判"文件没了"

  ③ 拷来拷去（cp / 网络传输）
     最后手段。能用 ① 就别用它。

  【判"挂载点/容器是否在位"的正确姿势】
    ✗ 别用 test -f <挂载点>/etc/os-release
      —— 很多发行版这个文件是**绝对软链**，从宿主根解析必然失败，
         于是你永远得到"容器没跑"的假结论
    ✓ 用 test -d <挂载点>/usr 或 test -x <挂载点>/bin/sh

━━ 5.5 容器里的生活规范（防乱） ━━

  给它一套固定目录，写进技能里：

    /workspace/tmp/      临时产物，随时可清
    /workspace/bin/      留着用的小工具
    /workspace/notes/    手册、记忆、待办（长期）
    /opt/<用户名>/bin/   正规命令
    /opt/<用户名>/{jobs,run,归档}/  后台脚本 / 脚本落地 / 退役品

  配套三个小命令（AI 自己会记得用）：
    清理   清临时目录（带 -n 干跑、-f 深清）
    备份   打包家当到公共存储
    自检   自检一遍

  再定两条硬规矩（写进技能里让 AI 遵守）：
    · 产出超过 200MB 或 100 个文件 → **先报告，问留哪些**
    · 动配置先备份，改动写进册子

  ⚠️ 这不是洁癖。AI 跑起来是真能一瞬间丢几百个文件的。

━━ 5.6 入口脚本要处理什么（checklist） ━━

  自己写一个 `xx` 脚本包住容器，至少覆盖：

  □ 执行命令（从 stdin 收，避免引号问题）
  □ 读写文件、列目录
  □ 路径互译（宿主路径 ↔ 容器路径）
  □ 后台任务 + 查日志
  □ 状态自检（容器在不在、挂载在不在）
  □ 容器启停（**start 要能等到挂载点就位再返回**）
  □ 容器运行日志（bind 失败这类静默错误只有它有）
  □ 空命令要报错（不然引号没包好时"命令消失"还显示成功）

【验收】
  容器里能读写宿主 App 的私有目录，两边看到的是同一份文件 → 过关。


╔══════════════════════════════════════════════════════════╗
║ 第 6 章 · 技能层：怎么把"手艺"固化下来                      ║
╚══════════════════════════════════════════════════════════╝

━━ 6.1 技能是什么（和提示词的分工） ━━

  提示词 = 它是谁（人格、态度、说话方式）—— **常驻**
  技能   = 这活怎么干（步骤、命令、坑）—— **按需加载**

  为什么要分开：
    · 提示词每轮都发，写太贵
    · 技能只在需要时读，能写得很细
    · 技能能单独更新、单独复用、单独给别人

━━ 6.2 SKILL.md 的规范 ━━

  ---
  name: 技能名（小写、连字符，和文件夹名一致）
  description: 一句话说清"什么时候该用我"
  ---

  # 标题
  ## 什么时候用
  ## 怎么干（步骤 / 命令 / 模板）
  ## 坑 / 注意

  可选配套：
    REFERENCE.md   详细资料（长表格、环境事实、坑清单）
    scripts/       附属脚本（入口脚本、工具）
    其他 .md       分层资料（比如 notes/ 下分主题）

━━ 6.3 description 决定生死（对比给你看） ━━

  ✗ 差的写法
    "这是一个操作容器的技能"
    → 太笼统，模型不知道该什么时候想起来

  ✓ 好的写法
    "在容器里跑命令、读写文件、传文件、跑后台任务、装包管 docker。
     当用户说「进容器跑一下」「容器里装个 X」「那台机器」时用它；
     容器与本机之间有直通挂载，读写不用搬。"
    → 说清了 **能力 + 触发词 + 关键前提**

  写好 description 的公式：
    **[能干什么] + [什么话该用我] + [一条最关键的前提/坑]**

━━ 6.4 技能的三种粒度（按需选） ━━

  ① 一句话技能
     就一段 SOP。适合："写日报的格式"、"回复客户的语气"
  ② 带文档的技能
     SKILL.md + REFERENCE.md。适合：某套系统的操作手册
  ③ 带脚本的技能
     SKILL.md + scripts/。适合：**要真干活**的（调接口、跑工具）
     → 脚本要能独立跑、参数明确、出错有提示

━━ 6.5 可抄的两个完整模板 ━━

  【模板一 · 流程类】

    ---
    name: 写日报
    description: 当我说"写日报""整理今天"时用它，把内容整理成固定格式。
    ---

    # 写日报
    ## 什么时候用
    我说"写日报""周报""整理今天"这类话的时候。

    ## 怎么干
    1. 先问我今天做了几件事（我没说就先问）
    2. 按下面格式输出，不要多写别的：
       日期：
       今日完成：- （一条一行）
       明日计划：- （一条一行）
       卡住的事：- （没有就写"无"）

    ## 注意
    - 不许编我没说的事
    - 一条不超过 20 字
    - 别加"加油""继续保持"这类废话

  【模板二 · 带脚本类】

    ---
    name: 出图
    description: 免 key 文生图。用户说"画一张""给我画""生成图片"时用它。
    ---

    # 出图
    ## 什么时候用
    用户要"画一张 / 生成图片 / 出张图"的时候。

    ## 怎么干
    1. 把用户描述整理成**英文提示词**（关键词用逗号隔开）
    2. 跑脚本：
       sh scripts/draw.sh "英文提示词" [宽] [高] [seed] [模型]
    3. 脚本会把图存进相册目录并打印路径
    4. 把路径贴回聊天

    ## 坑
    - **必须直连**，走代理会立刻失败（返回 000）
    - 脚本内限时 25 秒，超时就重试或换更短的提示词
    - 中文提示词效果差，先翻译成英文

  【每条技能都该有"坑"这一节】
  技能的意义就是把坑从你脑子里搬到纸上。

━━ 6.6 让 AI 自己写技能（具体话术） ━━

  直接说：

    "把刚才这套流程写成一个技能，按 SKILL.md 格式给我：
     name 用英文短横线，description 写清什么时候该用，
     正文分【什么时候用】【怎么干】【坑】三节。"

  它写完你要检查三样：
    ① description 里有没有**触发词**（"当用户说 XXX 时"）
    ② 步骤有没有**可检验的结果**（"跑完应该看到 XXX"）
    ③ 有没有把**刚才踩的坑**写进去

  改好之后挂到助手上，就算长在它身上了。

━━ 6.7 技能的维护 ━━

  · 版本：改动前先 cp -a 备份，或者整个目录留档
  · 命名：一张卡挂几个技能时，名字别太像（避免选错）
  · 冲突：两个技能都管同一件事 → 合并，或者把触发词写清楚区分开
  · 淘汰：三个月没用过的技能，删掉（技能库也会变重）

【验收】
  让它自己写一个技能、挂上、下次用起来 —— 三步都成 → 过关。


╔══════════════════════════════════════════════════════════╗
║ 第 7 章 · 云端层：出门办事                                  ║
╚══════════════════════════════════════════════════════════╝

━━ 7.1 什么时候你才需要云 ━━

  需要：
    · 要 24 小时在线（机器人、定时任务、Web 服务）
    · 要固定 IP / 端口
    · 要跑手机扛不住的东西（编译、爬虫、大模型推理）
  不需要：
    · 只是聊天、画画、写文档 → 手机足够了

  便宜方案：几十块一个月的小机器（2 核 2~4G）就够玩很久。
  学生机/活动机更便宜。

━━ 7.2 接进工具链（关键就三件） ━━

  ① 生成密钥、免密登录
       ssh-keygen -t ed25519
       ssh-copy-id 用户@IP
  ② 在**执行器所在的机器**上写 ssh config（注意不是在你手机上）
       ~/.ssh/config:
         Host 云
           HostName 1.2.3.4
           User 用户名
           IdentityFile ~/.ssh/id_ed25519
  ③ 让执行器支持 `ssh:别名` 这种 target
       → 工具层加一个分支，把命令原样丢给 ssh 跑

  【加上连接复用，体验完全不一样】
    ControlMaster auto
    ControlPath ~/.ssh/cm/%C
    ControlPersist 10m
    效果：第一次连 2 秒，后面 0.1 秒 —— 连续几十条远程命令也不难受。

━━ 7.3 远程命令的三个坑 ━━

  ① **远程 shell 不一定是你以为的那个**
     别人可能在用 zsh + 各种插件，`===`、`[方括号]` 会被当展开
     → 远程命令**引号包好**，或者干脆写成脚本再传过去跑
  ② **路径不做翻译**
     远程是远程的路径，本机是本机的路径，别混
  ③ **交互式命令会挂住**
     需要输入的东西一律别在自动流程里跑（会卡死到超时）

━━ 7.4 远程后台任务 ━━

  统一落一个目录，好找好清：
    ~/.rh-bg/<名字>.sh    脚本
    ~/.rh-bg/<名字>.log   日志
    ~/.rh-bg/<名字>.pid   进程号

  查状态：cat pid → kill -0 看还活着没 → tail 日志。

  ▸ 举例：一台轻量服务器上跑着 docker（两个机器人）、nginx 80、代理 7890。

【验收】
  一条命令发到云上跑，输出和你在电脑上 ssh 上去跑的一致 → 过关。


╔══════════════════════════════════════════════════════════╗
║ 第 8 章 · 自我进化：让 AI 改它自己                          ║
╚══════════════════════════════════════════════════════════╝

━━ 8.1 原理：配置存在哪 ━━

  大多数 App 的配置是本地文件（键值库/数据库/DataStore）。
  找到它，就能绕过 UI 直接改。

  ▸ 举例：RikkaHub 的配置全在一个 preferences_pb 里，值都是 JSON 字符串 ——
    用脚本读写它，这就是「改自己」。

  【为什么值得】
    · 批量改（7 张卡一次改完，不用戳 UI 一百下）
    · 程序化改（按规则生成、按条件筛）
    · 可备份可回滚（改前存一份）

━━ 8.2 改配置的四步铁律 ━━

  ① 备份：cp 原文件 原文件.bak.$(date +%Y%m%d-%H%M)
  ② 改：用脚本改，改完立刻**重新解析一遍**验证没坏
  ③ 生效：配置多半有缓存，**必须重启 App 进程**才读新值
     （延迟重启：写盘 → sleep 几秒 → kill 进程 → 系统自动拉起来）
  ④ 验证：重启后再读一遍，确认改动生效且没丢别的字段

  ⚠️ 顺序不能反。跳过 ① 的人，后面都在哭。

━━ 8.3 让 AI 改自己的提示词/技能（话术） ━━

  · 改提示词：
    "把我那个助手的系统提示词里 XX 那段改成 YY，改完备份，重启验证。"
  · 改技能：
    "把刚才这个坑补进 XX 技能的'坑'那一节，然后同步到两份目录。"
  · 造新东西：
    "照现在这套结构，给我新开一个 XX 技能，参考 YY 的写法。"

  三个前提（缺一个都别让它动手）：
    ① 有备份机制 ② 有重启机制 ③ AI 知道改完要验证

━━ 8.4 风控 ━━

  · 一次只改一件事（一次改五处，出错你不知道是哪处的锅）
  · 改完立刻验证（别等下次出问题才发现）
  · 敏感字段（密钥、账号）不要用脚本打印出来
  · 留一本"改动账"：什么时候改了什么、为什么、怎么回滚

【验收】
  你说一句"把 X 改成 Y"，它改完、重启、验证、汇报 —— 全程不用你动手 → 过关。

║ 第 9 章 · 复刻路线（按顺序，别跳）                          ║
╚══════════════════════════════════════════════════════════╝

  【阶段一 · 能聊天】门槛：无
    ✓ 装 App、配 API、建一个助手
    验收：能正常对话

  【阶段二 · 会写卡】门槛：会写字
    ✓ 写一张带完整人设的系统提示词
    ✓ 学会世界书（关键词触发）、预设消息
    验收：**换一个新对话，它还是那个味**

  【阶段三 · 有工具】门槛：无
    ✓ 开文件、命令、Python、剪贴板这些工具
    ✓ 建一个工作区，看它读写文件
    ✓ 装第一个技能（从 GitHub 导入 或 直接粘贴 SKILL.md）
    验收：**让它自己写一个技能，并真的用上**

  【阶段四 · 长出真手脚】门槛：要 root（有风险）
    ✓ 取得 root（KernelSU / Magisk）
    ✓ 装统一执行器到 /data/local/，chmod 755
    ✓ 给它加一个 root 模式，跑自检三连（id / hostname / ls /data/user/0）
    ✓ 立禁区和审批规则
    验收：**它在真机上跑出来的命令结果，和你手动跑的一致**

  【阶段五 · 给它一个家】门槛：root + 8G 空间
    ✓ 建容器（镜像 / 网络 / systemd / 用户 / 国内源）
    ✓ 配绑定挂载，做双向文件通道
    ✓ 写容器入口脚本（照第 5.6 的 checklist）
    ✓ 建目录规范 + 写进技能
    验收：**容器和手机两边看到同一份文件**

  【阶段六 · 出门办事 + 自我进化】门槛：钱
    ✓ 买机器、配密钥、写 ssh config、执行器加 ssh:分支
    ✓ 把踩过的坑一条条固化成技能
    ✓ 上"改自己"的通道（改提示词、改技能、改配置）
    验收：**你说"把刚才那套写成技能"，它写完、挂上、下次直接用**

  ━━ 每阶段的两个硬要求 ━━
  ① **产物必须落盘**（提示词落成卡、流程落成技能、环境落成脚本）
  ② **每阶段都要能验收**（写不出验收标准的自动化，都是赌博）


╔══════════════════════════════════════════════════════════╗
║ 第 10 章 · 通用坑规律（不是流水账，按"为什么"分类）          ║
╚══════════════════════════════════════════════════════════╝

  【A 时间类】
   A1 硬超时：单条命令 30 秒是常态 → 长任务一律后台
   A2 后台任务没有完成标记 → 你不知道它是跑完还是卡住
   A3 后台任务不继承环境变量 → 脚本里自己加载

  【B 身份类】
   B1 沙箱身份 ≠ 系统身份（uid 不一样，能碰的东西差一个数量级）
   B2 mount ns 遮蔽：裸 su 看到的不是全部 → 换执行器验证
   B3 容器里的普通用户，往往进不去宿主挂过来的目录

  【C 文件类】
   C1 FUSE 看创建者不看 mode（公共存储的读写规则）
   C2 容器 /tmp 是独立 tmpfs，和宿主不共享
   C3 绑定挂载的内容只在容器 namespace 里可见（宿主视角看不到）
   C4 中文路径要引号；文件名最好避开空格和怪符号

  【D 环境类】
   D1 容器没跑时，它的宿主挂载点是空的（别误判"文件没了"）
   D2 判断"某个东西在不在"，别依赖一个可能是软链的文件
   D3 远程 shell 可能是 zsh，特殊字符会被展开
   D4 家目录/工作目录在切换身份后会变（cd 一下再跑）

  【E 状态类】
   E1 配置有缓存：改盘 ≠ 生效，要重启进程
   E2 代理不是常开的：用前先探（curl -sI 目标 | head -1）
   E3 API 有速率限制：批量操作要退避重试
   E4 上下文是有限的：长对话要么压缩，要么开新对话

  【F 失败类】
   F1 **静默失败最可怕**：命令没跑却返回 0
       → 每个脚本结尾都要有明确的成功标记
   F2 空参数/空命令要报错，别当没事发生
   F3 报错信息会指向错误方向（"容器没跑"其实是判据写错了）
       → 先验证判据本身，再信它的结论

  【G 人的类】（最后但最重要）
   G1 没验收标准的自动化 = 赌博
   G2 没落盘的成果 = 没干
   G3 没备份的改动 = 早晚哭
   G4 一次改多处 = 出错了不知道谁的锅


╔══════════════════════════════════════════════════════════╗
║ 第 11 章 · 心法                                              ║
╚══════════════════════════════════════════════════════════╝

 ① **一层一层来。** 每层都能单独用，别一上来就冲 root + 容器 + 云。

 ② **每踩一个坑，就把它写成技能。**
    这是这套东西能"越用越聪明"的唯一原因。
    不写下来，你就是在原地踩同一个坑一百遍。

 ③ **给它一个家，比给它一堆工具重要。**
    固定目录、固定规矩、固定叫法 —— AI 才不会每次从零开始猜。

 ④ **凡是"它说干完了"，都要能验。**
    给每步配一个"应该看到什么"。

 ⑤ **手机能干的别上云，云上能干的别在手机上硬扛。**

 ⑥ **别把它当工具，当个住你隔壁的兄弟。**
    工具用完就扔；兄弟你会给他收拾房间、立规矩、
    犯错时骂两句再教一遍 —— 结果它真的会越来越顺手。

  【查故障，先问三句】
   1. 哪个身份在跑？（id / hostname）
   2. 目标在哪？（本机 / 容器 / 远程）
   3. 超时多少？（要不要后台）

  【自检五连】
   id && hostname && pwd && echo t > ./t && cat ./t

  【后台任务两段式】
   起：  systemd-run --unit=名字 --collect /bin/bash /路径/脚本.sh
   查：  systemctl is-active 名字; journalctl -u 名字 -o cat | tail -40

  【动配置四步】
   备份 → 改 → 重启进程 → 验证

  【写技能三件套】
   description 带触发词 / 步骤带验收 / 末尾写坑

  【判断容器在不在】
   test -d <挂载点>/usr   （别用 os-release，可能是绝对软链）

  【公共存储读写规矩】
   App 建占位 → root/容器原地覆盖（不许 mv）
