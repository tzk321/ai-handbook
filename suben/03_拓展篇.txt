━━ 12.1 为什么要租一台机器 ━━

手机上的 AI 有三个天生短板：

  ① 你睡觉它睡觉 —— 关机、锁屏省电、断网，它就不干活了
  ② 没有固定门牌号 —— 手机 IP 天天变，外面的服务找不到它
  ③ 关掉 App 就断 —— 前台的壳一没，后台线程也活不久

要在群里当机器人（第 13 章那种），这三条一条都不能有。
所以得起一台**服务器**：一直开着、有固定公网 IP、你 SSH 进去它就归你管。

  【一句话理解】
  服务器 = 一台放在别人机房里、永远开机、你能远程操作的电脑。
  性能不用好，稳就行。


━━ 12.2 买什么样的 ━━

  内存    2G 起步（跑两三个容器够用；要跑本地大模型才需要更大）
  CPU     2 核
  硬盘    40G 起（Docker 镜像很占地方，一个 astrbot 就 1G+）
  架构    **x86_64**（重要！后面说）
  系统    Ubuntu 22.04 / 24.04（网上教程最多，出问题好搜）

国内常见两家：阿里云「轻量应用服务器」、腾讯云「轻量应用服务器」。
学生认证能便宜不少；新用户首年经常几十块。

  【为什么强调 x86_64】
  有些容器镜像（比如某些数据库、语音识别）**只有 x86_64 版**，
  你买了 ARM 的机器，到时候 docker pull 直接报
  "no matching manifest for linux/arm64"，只能干瞪眼。

  ▸ 举例：轻量服务器，Ubuntu 22.04 LTS / x86_64 / 2 核 3.5G / 40G 盘

  【买完必须做的两件事】
  ① 安全组/防火墙：只放行你要用的端口（22、80、443，和后面要用的 WebUI 端口）
     —— 别图省事全放行，机器人服务器被扫是家常便饭
  ② 记下公网 IP、root 密码（或密钥）


━━ 12.3 第一次登上去 ━━

电脑上用 SSH（Windows 用 PowerShell，Mac 用终端）：

  ssh root@你的公网IP

输密码进去之后，先把系统更新一遍：

  apt update && apt upgrade -y

  【强烈建议：改成密钥登录】
  密码登录会被全世界的脚本一天扫几万次。改成密钥，扫描器直接没戏：

  1. 本地生成密钥（如果还没有）：ssh-keygen -t ed25519
  2. 把公钥传上去：ssh-copy-id root@你的公网IP
  3. 试一次能不能免密登录，**能了再**去服务器上关掉密码登录：
     编辑 /etc/ssh/sshd_config，设 PasswordAuthentication no
     然后 systemctl restart ssh

  ▸ 举例：在 ~/.ssh/config 里配个别名 `myserver`，
    以后 `ssh myserver` 就进去，不用记 IP 和端口。


━━ 12.4 装 Docker ━━

官方一键脚本（最省事，国内也能跑）：

  curl -fsSL https://get.docker.com | sh

装完验证：

  docker --version
  docker compose version

  【为什么要 compose】
  单个容器用 `docker run` 就够了。但只要超过两个容器要互相说话，
  `docker run` 就会变成一坨几十行的命令，改一个参数要从头再敲。
  compose 把这些写进一个 YAML 文件，一行 `up -d` 全起来。

  【常见坑】
  · 报 permission denied：加进 docker 组后要重新登录
      usermod -aG docker $USER
  · 国内 pull 不动：配镜像加速器（/etc/docker/daemon.json）
  · 磁盘满：`docker system prune -a` 清没用的镜像（小心，会删掉没在跑的）


━━ 12.5 Docker 的四个概念（记这四个就够） ━━

  镜像（image）  一张装好的光盘，只读。`docker pull nginx` 就是下光盘。
  容器（container）光盘放进播放机、按了播放 —— 一个运行中的实例。
                  同一个镜像能起好几个容器，互不干扰。
  数据卷（volume）容器里的东西删了就没了，重要的目录要"挂"到外面来。
                  compose 里写的 `./data:/AstrBot/data` 就是：
                  把当前目录的 data 接到容器里的 /AstrBot/data。
  网络（network） 容器默认各自孤立。放进同一个 network，才能用**容器名**互相访问。
                  这一条是第 13 章的关键 —— 记住。

  【最容易搞混的一句】
  端口映射 `"6185:6185"` 是"把你机器的 6185 转到容器的 6185"。
  冒号**左边是你（外网）**，右边是容器。只写左边，右边容器里要真有服务在听。


━━ 12.6 常用命令（背这 8 个） ━━

  docker ps                     看正在跑的容器
  docker ps -a                  连停掉的也看
  docker logs -f 容器名          看日志（-f 是持续跟，Ctrl+C 退出）
  docker exec -it 容器名 bash    钻进容器里看看（有的镜像没有 bash，换 sh）
  docker compose up -d          按 yml 起/更新容器（-d = 后台）
  docker compose down           停掉并删除容器（数据卷还在）
  docker compose pull           拉新镜像
  docker restart 容器名          重启

  【一条经验】
  compose 环境里，**尽量用 compose 命令，别用单个 docker 命令**。
  单条 docker restart 偶尔能让状态和 yml 对不上，下次 up 又变回去，白折腾。


━━ 12.7 目录怎么摆 ━━

一个项目一个目录，里面就三样东西：compose 文件 + 数据目录 + 日志。

  ~/app/
    ├── napcat/
    │   ├── docker-compose.yml
    │   └── data/          ← 挂出来的数据
    └── astrbot/
        ├── docker-compose.yml
        └── data/

好处：想备份就打包这个目录；想搬家就整个 scp 走。

  ▸ 举例：~/app/{astrbot,napcat,newapi,MaiBot}/，一个机器人一个目录

【验收】
  · 能 SSH 进去，且密码登录已关掉
  · `docker ps` 有输出不报错
  · 能说清"镜像 / 容器 / 数据卷 / 网络"分别是什么
  · 能看懂 `"6099:6099"` 哪边是哪边 → 过关

━━ 13.1 这俩各干什么（先看懂图，再动手） ━━

  ┌──────────────────────────────────────────────────────┐
  │                      你的服务器                        │
  │                                                        │
  │   ┌─────────────┐   反向WS     ┌──────────────┐        │
  │   │   napcat    │ ──────────▶ │   astrbot    │        │
  │   │（挂着QQ）    │ ws://astrbot │ （管着AI）    │        │
  │   │             │   :6199/ws   │              │        │
  │   └──────┬──────┘              └──────┬───────┘        │
  │          │                            │                │
  │          │ 收发QQ消息                   │ 调大模型API     │
  └──────────┼────────────────────────────┼────────────────┘
             ▼                            ▼
        腾讯的QQ服务器                  模型提供商
      （你在群里说的话）              （deepseek/等等）

  napcat   让程序能**收发 QQ 消息**的桥。它登录着你的 QQ 号，
           把收到消息翻译成统一格式发出去，把要回的话变成 QQ 消息发回来。
  astrbot  收下消息、交给大模型、把回答送回去的**大脑**。
           顺带管：白名单、唤醒词、人格、插件、联网搜索。

  为什么分开？各修各的：QQ 协议变了，只换 napcat；想换模型，只动 astrbot。
  而且 napcat 因为要模拟客户端，本身**不适合再背 AI 的活**，容易一起挂。


━━ 13.2 先把目录建好 ━━

  mkdir -p ~/app/astrbot/{data,napcat/config,ntqq}
  cd ~/app/astrbot

说明：
  data/           astrbot 的全部数据（配置、数据库、插件）
  napcat/config/  napcat 的配置（登录信息、要不要连谁）
  ntqq/           QQ 本体数据（登录态缓存在这，删了要重新扫码）


━━ 13.3 docker-compose.yml（抄这份） ━━

  # ~/app/astrbot/docker-compose.yml
  services:
    napcat:
      image: mlikiowa/napcat-docker:latest
      container_name: napcat
      restart: always
      environment:
        - TZ=Asia/Shanghai
      ports:
        - "6099:6099"                      # WebUI：扫码登录、看连接状态
      volumes:
        - ./napcat/config:/app/napcat/config
        - ./ntqq:/app/.config/QQ
      networks: [qqbot]

    astrbot:
      image: soulter/astrbot:latest
      container_name: astrbot
      restart: always
      environment:
        - TZ=Asia/Shanghai
      ports:
        - "6185:6185"                      # WebUI：配模型、配平台
      volumes:
        - ./data:/AstrBot/data
      networks: [qqbot]

  networks:
    qqbot:
      driver: bridge

  【注意三处】
  ① 两个服务写在**同一个 network**（qqbot）里 —— 不然它们互相看不见，
     后面 `ws://astrbot:6199` 里的 `astrbot` 就解析不出来
  ② napcat **只暴露 6099**。6199 是 astrbot 的监听口，只给容器内部用，
     **千万别映射到公网**
  ③ `restart: always` —— 服务器重启后自动拉起来，这条不能省

  【密钥和 token 写哪】
  上面没出现任何密码，这是**故意的**。需要密码的地方（后面几处），
  值放在 **astrbot 的 WebUI 里填**，别写进 yml —— yml 万一传出去就全泄了。


━━ 13.4 起来 ━━

  docker compose up -d
  docker compose ps          # 两个都该是 running

第一次拉镜像慢，等几分钟。看着点：

  docker compose logs -f astrbot

看到类似 "WebUI 启动在 0.0.0.0:6185" 就成了，Ctrl+C 退出。


━━ 13.5 登录 QQ（扫码） ━━

浏览器打开：`http://你的IP:6099`

  · 它会让你登录 WebUI（首次可能用默认 token，看 `docker logs napcat` 里打印的）
  · 进去后找「网络配置」或「QQ 登录」，会出现一个**二维码**
  · 用你要做机器人的那个 QQ 手机端扫它

  【三条经验】
  ① 别用主号！用小号。协议登录有被风控的风险，主号丢了不值当
  ② 扫码后别马上关页面，等它显示"在线"
  ③ 这个登录态存在 `./ntqq` 里，**别删**，删了下次又要扫码

  ▸ 举例：napcat 的登录态放在 app/astrbot/ntqq/，
    config 里能看到 napcat_<QQ号>.json / onebot11_<QQ号>.json


━━ 13.6 把两根线接上（最关键的一步） ━━

两根线：napcat 要"往外发"，astrbot 要"等着收"。方向是 napcat → astrbot。

  【A. napcat 这头：加一个「反向 WebSocket 客户端」】
  在 napcat 的 WebUI（6099）里找「网络配置」→ 新增 → 选 **WebSocket 客户端**（反向）：

    URL       ws://astrbot:6199/ws
    Token     自己编一串（比如 my-token-123456）
    启用       开

  逐字解释这个 URL：
    ws://        WebSocket 协议
    astrbot      **容器名**（同一个 network 里，Docker 自带 DNS 能解析）
    6199         astrbot 在容器内部监听的端口
    /ws          固定的路径，不能省

  【B. astrbot 这头：加一个平台适配器】
  打开 astrbot 的 WebUI（6185）→ 「平台」→ 新增 → 选 **aiocqhttp**（QQ 个人号）：

    类型        aiocqhttp
    反向 WS 端口  6199
    Token        **跟上面那头一字不差**

  保存、启用。

  【对不上的三个地方，按顺序查】
  ① Token 不一样 —— 最常见。两边各粘一次，别一个用引号一个没用
  ② URL 里的容器名写错了 —— 必须是 compose 里的服务名/container_name（astrbot）
  ③ 不在同一个 network —— 回看 13.3 的第 ① 条

  连上之后，napcat 的日志会显示心跳；astrbot 的平台页会变「已连接」。


━━ 13.7 配 AI 模型 ━━

astrbot WebUI → 「服务提供商」→ 新增：

  类型      OpenAI 兼容（大部分中转/官方都是这个）
  API Base  https://你的服务商/v1
  API Key   sk-xxxxx
  模型       填一个能用工具调用的（建议先从便宜的试）

保存后回「配置文件」把默认用的模型指过去。

  【省钱提醒】
  群聊场景消息量很大。先用**最便宜的模型**跑通，确认没问题再换好的。
  见第 16 章（自建 API 中转）。


━━ 13.8 唤醒词和白名单（不设会破产） ━━

群里的机器人不能每条消息都回 —— 不然一天能烧掉你一个月额度。

  【唤醒词 wake_prefix】
  只有消息里带这些词才搭理。例如设成：`ai`、`/`、`bot`
  群里就得 @它 或打 `ai 在吗` 它才回。

  【白名单 id_whitelist】
  只服务指定的群和好友，其他一律不理。格式长这样：

    napcat:GroupMessage:123456789     ← 某个群
    napcat:FriendMessage:987654321    ← 某个好友

  这两个一起设，是"让它只在我想要的地方说话"的双保险。

  ▸ 举例：唤醒词设成 `ai` / `/`；白名单里挂一个群 + 几个好友。
    格式就是上面那样，前缀 `napcat` 跟平台适配器的 id 对应。

  【管理员 admins_id】
  填你自己的 QQ 号，管理员才能用重启、插件管理这类命令。


━━ 13.9 测试 ━━

1. 用另一个号（或让朋友）在那个群里发：`<唤醒词> 你好`
2. 看 napcat 日志有没有收到消息
3. 看 astrbot 日志有没有在调模型
4. 群里应该回出来了

三步都不动，就是三根链子中的一根断了：QQ→napcat→astrbot→模型，按这个顺序查。

【验收】
  · napcat 里 QQ 显示在线，且登录态已落到磁盘（ntqq 目录里有东西）
  · astrbot 平台页显示「已连接」
  · 群里发唤醒词 + 一句话，它答上来了
  · 6199 **没有**出现在你服务器的公网端口列表里 → 过关

━━ 14.1 微信和 QQ 不一样，先选路 ━━

QQ 有 napcat 这种成熟方案，微信没有"免费又稳又合规"的中间态。三条路：

  路子          门槛              稳定性        封号风险   适合
  ────────────────────────────────────────────────────────────────
  个人微信       扫个码就行          看运气         **有**    自己玩/小号
  企业微信       注册个企业（免费）    高            无       正经用/团队
  微信公众号      要认证（个人号也行）  高            无       对外服务

  【一句话建议】
  只是自己想玩 → 个人微信，但**用小号**。
  要给一群人用 → 企业微信，稳，还不要钱。
  要对外做服务 → 公众号。

  另外 astrbot 还支持一堆别的平台（telegram / 飞书 / 钉钉 / Discord /
  Slack / KOOK / Line / Misskey / Mattermost），配法大同小异：
  拿凭据 → 在 WebUI 里新增平台 → 填进去 → 启用。


━━ 14.2 个人微信 ━━

astrbot 里内置了适配器，注册名叫 `weixin_oc`（界面上显示「个人微信」）。

  步骤：
  1. astrbot WebUI → 平台 → 新增 → 选「个人微信」
  2. 保存启用后，日志/页面里会给出一个**登录二维码**
  3. 用微信扫码
  4. 扫完状态变「已连接」，就能收发消息了

  【先说清楚风险，别怪没人提醒】
  · 这是**非官方协议**，腾讯随时可能风控
  · 万一被封，是**整个微信号**的事，聊天记录也一起没
  · 所以：**别拿主号试**。专门注册个小号，只用来当机器人
  · 别拿它群发、别加陌生人、别刷得太频繁 —— 这几点最容易触发风控

  【和 QQ 那套的分工一样】
  微信群里的消息也要靠唤醒词和名单过滤，不然一样烧钱。
  唤醒词、白名单在 astrbot 的「配置」里改，和 QQ 共用一套逻辑。


━━ 14.3 企业微信 ━━

公司/团队用，稳定合规。个人也能注册个"企业"（一个人也算）。

  大概流程：
  1. 注册企业微信 → 记下「企业 ID」（corp_id）
  2. 后台建一个自建应用 → 拿到 Secret 和 AgentID
  3. 配一个"接收消息的地址"（要么有公网域名，要么用它的回调接口）
  4. astrbot 里新增平台，选 wecom / wecom_ai_bot，把上面三样填进去

  【它和 QQ 那套最大的不同】
  企业微信**要公网能访问你**（回调），所以：
  · 你得有域名，并且配好 HTTPS（见第 15.6 节）
  · 服务器防火墙要放行
  这也是为什么它比个人微信"稳"——走的是官方接口，不模拟客户端。


━━ 14.4 一个号同时挂好几个平台 ━━

astrbot 支持同时启用多个平台适配器。比如：

  napcat   （QQ 个人号）
  weixin_oc（个人微信）
  telegram

同一个大脑、同一套人格，你在哪个平台说话它都能接。
这对"人设一致性"很有用 —— 写一次提示词，到处是同一个它。

【验收】
  · 至少接通一个平台，能收能回
  · 个人微信那条：**确认用的不是主号**
  · 异常消息（没带唤醒词的）确实不会被回 → 过关

║ 第 15 章 · 稳住它（自启 / 备份 / 升级 / 安全 / HTTPS）    ║
╚══════════════════════════════════════════════════════╝

机器人这东西，搭起来只花一小时，养着才是日常。
这一章全是"出事之前就该做"的事。


━━ 15.1 开机自启（两层，缺一不可） ━━

  第一层：容器层 —— compose 里的 `restart: always`
          它管的是"容器挂了自动重启"

  第二层：系统层 —— Docker 服务本身要开机自启
          它管的是"服务器重启后，Docker 自己起不起来"

  systemctl enable docker
  systemctl is-enabled docker      # 输出 enabled 才对

  两层都配好，服务器被重启（比如被机房维护）后，你的机器人会自己回来。


━━ 15.2 备份（最容易被跳过，最容易后悔的一条） ━━

  【备份什么】
  就备份那个项目目录 —— 里面有数据库、配置、登录态，全在里面：

    tar czf ~/backup-$(date +%F).tgz -C ~/app astrbot

  【多久备一次】
  手动不行，人一定会忘。挂个定时任务，每天凌晨打包，只留最近 7 份：

    crontab -e
    # 加这一行（每天 4 点备份，删掉 8 天前的）
    0 4 * * * tar czf /root/backup-$(date +\%F).tgz -C /root/app astrbot && find /root -name 'backup-*.tgz' -mtime +7 -delete

  【备份放哪】
  放同一台机器上等于没备份 —— 机器一坏全没。
  至少做到下面之一：
  · scp 到自己的电脑（手动/脚本）
  · 传到对象存储（阿里云 OSS / 腾讯云 COS，几块钱一年）
  · git 私有仓库（适合纯文本配置，不适合大数据库）

  【关键：备份要试过恢复】
  没验证过能恢复的备份 = 没有备份。找个周末，把 tgz 解开看看目录全不全。

  ▸ 举例：用这招保住过手机端的聊天库，
    同一套思路 —— **先有后悔药，再动手**。


━━ 15.3 升级 ━━

  改配置和 yml 之后：
    docker compose up -d          ← 只重建有变化的部分

  跟镜像更新：
    docker compose pull
    docker compose up -d

  【什么时候别升】
  · 正在被用着的时候（群里有人聊天）
  · 没备份的时候
  · 看到新版本有 breaking change 的说明，但你没空看文档的时候

  【升坏了怎么办】
  数据在 ./data 里没动，镜像回退就行：改 yml 里的 tag（比如 :latest → :4.28.0），
  再 up -d。所以 —— **重要项目别用 latest，钉版本号**。


━━ 15.4 看日志（出事第一件事） ━━

  docker compose logs -f astrbot         跟实时日志
  docker compose logs --tail=200 napcat  看最后 200 行
  docker logs -f astrbot 2>&1 | grep -i error    只看报错

  【日志总在刷屏咋办】
  两个都开日志文件，定期清。astrbot 的配置里有 log_file_enable 这类开关，
  napcat 也有对应的设置。

  【判断"是不是 OOM 杀的"】
  容器莫名其妙重启、日志断层，多半是内存不够被系统杀了：

    dmesg | grep -i "killed process"
    docker inspect 容器名 | grep -i oom

  2G 内存的机器，两个容器 + 数据库就到边了。加 swap 能顶一阵：

    fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
    echo '/swapfile none swap sw 0 0' >> /etc/fstab


━━ 15.5 安全五件事 ━━

  ① **密钥登录，关掉密码登录**（第 12.3 节）。这一条能挡掉 99% 的扫描。
  ② **服务器防火墙只开必要的口**

      ufw allow 22/tcp
      ufw allow 80,443/tcp
      ufw enable
      ufw status

     注意：阿里云/腾讯云还有一层「安全组」，**两层都要改**，只改一层等于没改。
  ③ **内部端口永远不要暴露** —— napcat 的 6199、数据库的 5432/6379，
     它们只在容器网络里用，公网一个都别开。
  ④ **fail2ban**：自动封禁反复试密码的 IP。默认配置就够：

      apt install fail2ban -y
      systemctl enable --now fail2ban

  ⑤ **WebUI 全都要密码**。astrbot 的 6185、napcat 的 6099，
     默认可能没有或很弱。设强密码，能开两步验证就开。

  【一条铁律】
  凡是"我临时开一下方便调试"的端口，调试完**立刻关**。
  暴露在公网的机器人后台被扫到，只是几小时的事。


━━ 15.6 给它个域名和 HTTPS ━━

  【为什么要】
  · 浏览器不再报"不安全"，手机端调用也更放心
  · 企业微信那种回调**强制要求** HTTPS
  · 以后想接网页版、想分享给别人，都得有域名

  【最省事的路子：Caddy】
  它自动申请、自动续期证书，配置文件短到离谱。

  在项目目录里加一个 caddy 服务：

    # docker-compose.yml 里追加
    caddy:
      image: caddy:2
      container_name: caddy
      restart: always
      ports:
        - "80:80"
        - "443:443"
      volumes:
        - ./Caddyfile:/etc/caddy/Caddyfile:ro
        - caddy_data:/data
      networks: [qqbot]

    # 同目录新建 Caddyfile（把域名换成你自己的）
    bot.你的域名.com {
        reverse_proxy astrbot:6185
    }

  然后 `docker compose up -d`。第一次访问它会自动去申请证书（要 80 端口通、域名已解析）。

  【DNS 别忘】
  在域名商那边加一条 A 记录：`bot.你的域名.com → 你的服务器 IP`。
  解析生效要几分钟到几小时。

  【反代之后注意】
  · 原来的 6185 端口可以关掉了（只留 Caddy 的 80/443），少一个暴露面
  · 如果 WebUI 有"信任代理头"之类的开关，Caddy 反代时可能要打开，
    否则日志里看到的全是 127.0.0.1


━━ 15.7 每天 30 秒巡检 ━━

养成顺手看一眼的习惯，比出事再查强十倍：

  docker ps                    两个容器在不在、跑了多久（Up 时间短 = 刚重启过）
  df -h                        磁盘还剩多少（Docker 很吃盘）
  free -h                      内存够不够
  docker compose logs --tail=50 astrbot    有没有报错在滚

  【一个小脚本】
  把这四条塞进一个 sh，每天跑一次，十秒钟看完。

【验收】
  · 重启服务器，两个容器自己回来了
  · 备份定时任务在跑，且**你验证过能解开**
  · `ufw status` 里只有一个 22（+80/443），没有 6199 / 5432
  · 域名能打开 WebUI，地址栏是小锁头 → 过关

║ 第 16 章 · 自建 API 中转（花一样的钱，多用好几倍）        ║
╚══════════════════════════════════════════════════════╝

━━ 16.1 它解决什么问题 ━━

用久了会遇到三件事：

  ① 换一家服务商，就要把每个客户端（手机 app、astrbot、脚本）都改一遍
  ② 手里有好几家的 key，想知道各自还剩多少钱、用了多少，只能一家家登
  ③ 有的客户端只支持 OpenAI 格式，但你用的服务商是别的格式

  中转站的思路：**在你自己的服务器上开一个"统一入口"**，
  所有客户端只连它，它在后面管着 N 家真服务商。

  客户端 ──▶ 你的中转站 ──▶ deepseek / 通义 / 智谱 / ...
                （记账、限速、换家）

  好处：客户端配置永远不用改；后台能看到谁用了多少；
        可以给不同的人发不同的子 key。

  ▸ 举例：服务器上跑着 new-api，映射在 2999 端口。


━━ 16.2 new-api / one-api 是什么 ━━

社区里最常见的两个开源实现，new-api 是 one-api 的加强版（界面和功能更多）。
都是单容器 + 一个数据库，起起来很快。


━━ 16.3 起一个（compose 模板） ━━

  # ~/app/newapi/docker-compose.yml
  services:
    new-api:
      image: calciumion/new-api:latest
      container_name: new-api
      restart: always
      command: --log-dir /app/logs
      ports:
        - "2999:3000"                       # 左边你可以随便改
      volumes:
        - ./data:/data
        - ./logs:/app/logs
      environment:
        - SQL_DSN=postgresql://root:改我@postgres:5432/new-api
        - REDIS_CONN_STRING=redis://:改我@redis:6379
        - TZ=Asia/Shanghai
        - NODE_NAME=new-api-1
      depends_on: [redis, postgres]
      networks: [newapi]

    redis:
      image: redis:latest
      container_name: redis
      restart: always
      command: ["redis-server", "--requirepass", "改我"]
      networks: [newapi]

    postgres:
      image: postgres:15
      container_name: postgres
      restart: always
      environment:
        POSTGRES_USER: root
        POSTGRES_PASSWORD: 改我
        POSTGRES_DB: new-api
      volumes:
        - pg_data:/var/lib/postgresql/data
      networks: [newapi]

  volumes:
    pg_data:

  networks:
    newapi:
      driver: bridge

  【三处密码必须改】
  ⚠️ 模板里所有 `改我` 都换成强密码，**三处要一致**（DSN 里写的和下面设的要对上）。
  官方模板默认是 123456，不改就是给全网开门。

  【为什么不用 SQLite】
  能跑，但多容器并发下容易锁。有自己的库更稳，反正 postgres 也是白送一个容器。


━━ 16.4 起好之后 ━━

  1. `docker compose up -d`，浏览器开 `http://你的IP:2999`
  2. 首次登录默认账号 root / 123456 —— **第一件事就是改掉**
  3. 进「渠道」→ 新增 → 选服务商类型（OpenAI 兼容最常用）→ 填你原来的
     base_url 和 key → 测试一下能不能通
  4. 进「令牌」→ 新建一个 token —— 这就是你客户端要用的 `sk-xxx`
  5. 以后客户端统一填：`http://你的IP:2999/v1` + 这个 token


━━ 16.5 接进你的各处客户端 ━━

  手机上的 RikkaHub：
    提供商 → API Base URL 填 `http://你的IP:2999/v1`（或域名）
    API Key 填刚建的令牌 → 拉模型列表，选一个 → 保存

  astrbot：
    服务提供商 → 类型 OpenAI 兼容 → 同样填中转站的地址和令牌

  **好处立刻体现**：以后换服务商，只在 new-api 后台加个渠道，
  手机和 astrbot 一个字都不用改。


━━ 16.6 别把它变成公共厕所 ━━

  ① 别把 2999 直接晾在公网 —— 要么套 HTTPS（第 15.6 节），要么只给自己 IP 用
  ② 后台密码改强，能开两步验证就开
  ③ 给不同的用途发不同的子令牌，谁超支了单独停谁
  ④ 定期看「日志」页，异常调用一眼能看出来

  【一条经验】
  中转站是"你自己的基础设施"，不是"免费给朋友用"的福利社。
  真给人用，一定要设额度上限。

【验收】
  · 一个令牌能在手机 RikkaHub 上正常聊天
  · 后台「日志」里能看到这次调用
  · 后台默认密码已改 → 过关


╔══════════════════════════════════════════════════════╗
║ 第 17 章 · 拓展排错手册（对号入座）                      ║
╚══════════════════════════════════════════════════════╝

【装 Docker / 起容器】

  docker: command not found        没装好或没重登 shell
                                   → 重开一个 SSH 会话，或 usermod -aG docker $USER 后重登
  permission denied /var/run/...   当前用户不在 docker 组
                                   → 同上（或用 sudo）
  pull 很慢、超时                  国内直连慢
                                   → 配 daemon.json 镜像加速器，或用能通的网络
  no matching manifest for arm64   镜像没有 ARM 版
                                   → 换 x86_64 机器，或换一个有 ARM 版的镜像
  port is already allocated        端口被占了
                                   → docker ps 看谁占的；ss -tlnp | grep 端口
  compose 文件报 yaml 错            多半是**缩进**（YAML 只认空格，不认 Tab）
                                   → 全用空格，层级对齐

【容器起来了又挂】

  一直 Restarting                 看日志：docker compose logs --tail=100 服务名
                                  常见：配置写错、缺环境变量、连不上数据库
  被系统杀掉（OOM）                 内存不够 → free -h / dmesg | grep -i killed
                                  加 swap，或降配（少开容器）
  日志里时间不对                   缺 TZ=Asia/Shanghai
  中文日志乱码                     容器内没有中文字体（装 t2i / 截图类插件时会遇到）
                                  镜像里补字体包

【QQ 那套不通】

  napcat 里 QQ 显示离线            登录态过期
                                   → 进 6099 重新扫码；确认 ntqq 目录没有被删
  astrbot 平台页一直「未连接」       三查：Token 是否一字不差 / URL 里容器名是否是 astrbot /
                                   两个服务是否在同一个 network
  napcat 日志有连接但 astrbot 收不到  反向 WS 的路径漏了 /ws
  消息能收但不回                    ① 没带唤醒词 ② 不在白名单 ③ 模型没配或没额度
                                   → 挨个查，日志里会写"忽略"之类的原因
  群里回两遍                        有两个平台适配器同时启用了
                                   → 关掉不用的那个

【微信】

  扫码后很快掉线                    风控或协议变动
                                   → 换小号；隔天再试；看适配器日志的具体错误码
  能收不能发                        有的消息类型不支持
                                   → 看适配器日志，通常是媒体类消息的格式问题
  整个号被封                         用了非官方协议
                                   → 无解。这就是为什么反复强调：**别用主号**

【中转站】

  令牌报 401                        令牌没启用 / 过期 / 额度用完
  渠道报错 upstream error           渠道的 key 或 base_url 不对
                                   → 后台点「测试」逐个验证
  用量对不上                        多家渠道的计费口径不同
                                   → 以后台汇总为准，别拿服务商账单硬对

【网络 / 域名】

  域名打不开                        ① DNS 没生效 ② 安全组没放 80/443 ③ Caddy 没起来
                                   → dig 域名看解析；ufw status 看端口
  证书申请失败                      80 端口不通（Caddy 要先用 80 验证）
                                   → 放行 80，再 up -d
  从外网访问不了，本机 curl 正常      防火墙/安全组没放行（两层都要看）

【一条通用心法】
  分层看：**网络 → 容器 → 应用 → 配置**，一层一层往下。
  先在服务器本机 curl 通，再谈外网；先看容器在不在跑，再谈应用报什么错。
  90% 的"玄学问题"，都是跳过了其中一层直接猜。

【验收】
  · 遇到问题能先说出"是哪一层"，再去动手
  · 能背出 QQ 那套最难的三处（Token / 容器名 / 同网络）
  · 知道"备份没验证过 = 没备份" → 过关
